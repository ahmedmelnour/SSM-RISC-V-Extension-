## 2. Hardware: 32 KB → 128 KB RAM (STATUS §7.1)

The stated blocker for Step 3: a 20k-parameter INT8 model was at the 32 KB
ceiling and 50k did not fit at all.

**Changed**

| File | Change |
|---|---|
| `rtl/a7lite_soc_top.sv` | `MEM_WORDS` 8192 → 32768; added `IDX_W`; `ia`/`da` widened |
| `fw/link.ld` | `LENGTH` 32K → 128K |
| `fw/build.sh` | `MEM_WORDS` → 32768 |
| `README.md`, `fw/main.c` | memory-map table and boot banner |

The index widths are now **derived** from `MEM_WORDS` (`IDX_W = $clog2(MEM_WORDS)`)
rather than written out as `[12:0]`. This is deliberate: the abandoned SoC in
`doc/BRINGUP.md` §10.2 died from exactly this class of bug — an 8192-entry array
indexed with `addr[16:2]`, silently aliasing. Deriving the width makes that
mismatch unrepresentable.

**How it was verified** — three independent ways, because synthesis passing is
not evidence that the address decode works:

1. **Resource** — exactly **32 RAMB36** (64% of 50), as §7.1 predicted, 18 spare.
   LUTs 3724 (17.9%), FF 2299 (5.5%), DSP 3. LUTs went *down* 9.
2. **Timing** — **WNS +2.360 ns**, WHS +0.092 ns → Fmax ≈ 56.7 MHz, ~13% margin
   at 50 MHz. This is *better* than the 32 KB build's +1.660 ns. Widening cost no
   timing at all; the critical path was never the memory decode. Treat the gain as
   placement noise, not a real headroom increase.
3. **Function** — programmed the board and re-ran the benchmark suite. All five
   kernels reproduce the 32 KB baseline **bit-identically** (cycles, instret,
   loads, stores). Saved as `results/mem128k_20260809_064445.csv`.

That third check is the one that matters: it means every number in STATUS §6
stays comparable against anything measured from here on.

## 4. Dataset: MIT-BIH

### 4.1 Fetching — `py/fetch_data.py` (new, 123 lines)

`wfdb.dl_database('mitdb', ...)` was tried first and abandoned. It is the wrong
tool here for two reasons that only show up on a slow link:

- **No timeout.** It sat on a dead socket for 8+ minutes on record 203 with no
  output, and there is no way to distinguish that from slow progress.
- **Not resumable.** It downloads the database as one operation; an interruption
  leaves nothing usable, so every retry starts over.

PhysioNet also throttles to about **13 KB/s per connection** (measured: 2m25s for
a single 1.95 MB record), which makes a serial fetch of ~100 MB take over an hour.

The replacement fetches **12 files concurrently**, with connect/read timeouts, up
to 4 retries each, and writes to a `.part` renamed only on success so a truncated
file can never masquerade as complete. A record counts as present only when all
of `.dat`/`.hea`/`.atr` exist. Re-running costs only what is missing.

Result: **48/48 records, 90 MB, zero failures**, in a few minutes.

### 4.2 Preprocessing — `py/prep_data.py` (new, 218 lines)

Produces `py/data/beats.npz` + `beats.json`. The int16 windows here are the
shared input for the float model, the quantized model, the fixed-point reference
and the C port — none of them re-derive their own inputs, which is what makes the
eventual bit-exactness claim mean anything.

Decisions that most affect whether the numbers are defensible:

- **Inter-patient split (de Chazal 2004 DS1 train / DS2 test)**, not a random beat
  split. Beats within a recording are near-duplicates; a random split reports ~99%
  accuracy that collapses on a new patient. This is the first thing an examiner
  who knows the dataset will check.
- **Paced records 102/104/107/217 excluded**, per AAMI EC57.
- **MLII selected by name, not index** — it is channel 1 in record 114 and channel
  0 elsewhere. Hardcoding 0 silently trains on a different lead for that record.
- **Annotated R-peaks used for segmentation**, not a detector — conventional for
  this benchmark, but it must be stated (see open question 2 below).
- **int16, millivolts in Q3.13** (1 mV = 8192 counts). A power-of-two scale keeps
  the later fixed-point work to shifts.
- Per-window median subtraction for baseline removal.

**Validated, not assumed:**

- 51,000 train / 49,693 test beats — matching the standard de Chazal counts.
- R-peak actually centred: median argmax|x| = 65 against a centre of 64; **97.8%
  within ±8 samples**.
- Clipping negligible: 39 of 6.5M samples (0.0006%).
- V beats have **2.3× the mean amplitude of N** — physiologically correct, and
  independent evidence that labels line up with windows.

### 4.3 Window widened to ~3 beats (second revision)

Initial config was 128 samples at 180 Hz — one beat. Training run #2 showed, after
one epoch, **V at 68.5% sensitivity / 97.5% precision and S at exactly 0.00%**.

That is not a training failure, it is the framing. Supraventricular ectopic (S)
beats are largely *normal in morphology*; what identifies them is that they arrive
**early**. A short window centred on the R-peak deletes precisely that information.
de Chazal's original work feeds explicit RR-interval features for this reason.

Rather than bolt hand-engineered RR features onto the input, the window was
widened so the neighbouring beats are inside it and the sequence model can see the
rhythm itself. This keeps the SSM as the thing doing the work — the point of the
project — and makes T *larger*, so the scan the accelerator targets grows rather
than shrinks.

- **288 samples at 120 Hz = 2.40 s** (decimation 2 → 3; Nyquist 60 Hz, still well
  above the ~40 Hz where QRS energy lives, so V morphology should be unharmed).
- Verified: **mean 3.12 R-peaks per window; 90.3% contain ≥3 beats, 100% ≥2.**
- Cost: scan work is O(T), so this is **2.25× the compute per inference**.

Counts after the change: 50,951 train / 49,651 test (marginally fewer, as more
windows run off the ends of records).

**Outcome: S learns, but late and slowly.** Per-epoch S sensitivity on validation:

```
ep  1     2     3     4     5     6     7     8
    0.00  0.00  0.44  0.88  0.00  1.10  0.22  0.66
ep  9     10    11    12    13    14    15
    0.88  1.75  1.54  3.73  3.73  1.10  13.38
```

**A methodological warning, recorded because it nearly became a wrong
conclusion in this document.** Through epoch 14 this looks exactly like noise
around zero, and it was written up here as "necessary but not sufficient — the
model cannot learn S." Then epoch 15 jumped 12x, as the cosine learning-rate
schedule decayed. The earlier reading was premature.

The lesson generalises past this experiment: a rare class emerging only once the
learning rate decays is a normal pattern, not an anomaly, and **a flat minority-
class metric during the high-LR phase is not evidence of anything.** Do not
conclude a class is unlearnable before the schedule has annealed. Anywhere this
project compares configurations on a rare class — the coupling sweep included —
the comparison has to be made at the *end* of an equal schedule, not partway.

S at 13.4% sensitivity / 10.0% positive predictivity is still weak clinically,
and it remains the class that caps macro-F1: at epoch 15 the split is
N 0.919, S 0.114, V 0.783 → macro 0.605. So the case for explicit RR-interval
features (pre-RR, post-RR, ratio to a local average — what de Chazal used) is
still open, and they are cheap: three extra scalar inputs that do not touch the
scan and so cost essentially nothing in the accelerated path. But it is now a
question of *how much better*, not of whether S is learnable at all.

Do not silently drop S from the reported classes to make the table look better;
S is one of the two clinically important AAMI classes, alongside V.

## 5. Model — `py/model.py` (new, 145 lines)

`ECGNet`: input projection → 2 × `SelectiveSSM` (D=32, N=16, pre-norm residual)
→ mean pool → linear head. **7,781 parameters = 7.6 KB as INT8**, inside the
≤10k budget (d_model=48 would be 14,709, over).

Two choices are claims to defend in the writeup, not implementation details:

- **Selective, not time-invariant.** `dt`, `B` and `C` are projections of the
  input and change every timestep. This is what makes the scan worth accelerating
  — the coefficients cannot be hoisted out of the loop — and it matches the shape
  `ssm_scan_q15` in `fw/bench.c` already measured.
- **Forward-Euler discretisation, `a = 1 − dt·A` clamped to [0, 0.999)**, instead
  of Mamba's `a = exp(dt·A)`. Exact `exp` in fixed point needs a lookup table and
  argument reduction on a core with no FPU, *inside the loop being accelerated*.
  Euler is one multiply and one subtract, and is stable exactly when `dt·A < 1`,
  which the clamp enforces. This **changes the model**, so accuracy must be
  compared against this model trained this way — never against a Mamba baseline
  that used `exp`.

### `py/test_model.py` (new, 105 lines)

The scan is written for autograd efficiency (§6.1), and optimised code that
silently computes something *slightly* different is the worst possible failure
here — it would be quantized, ported to C, and matched bit-for-bit against the
wrong model, with every downstream check passing. So it is guarded:

- fast scan vs a naive triple-nested-loop transcription of the recurrence:
  **max abs err 5.96e-08** (float32 epsilon)
- large-`dt` stability: output stays finite, so the clamp holds
- zero input → exactly the bias path, catching a constant leaking into the scan
- parameter budget assertion

All pass.

## 6. Problems hit, and what they actually were

This section is the most valuable part of the log. Four of these cost real time.

### 6.1 Scan backward was 14× its forward

Symptom: forward 0.74 s, backward **10.56 s** at batch 256. Normal ratio is ~2×.

Cause: the first version precomputed `a` for all timesteps as a `[B,T,D,N]` tensor
and then used `a[:, t]` inside the loop. Each `select` backward allocates and
zeros a gradient buffer the size of the **whole** tensor — 67 MB at batch 256 —
once per timestep, 128 times per layer.

Fix: `.unbind(1)` once, which lowers to a single `stack` in backward. Backward
0.42 s; epoch time **1825 s → 116 s**.

> If the scan ever feels inexplicably slow again, look for a `[:, t]` on a large
> tensor before looking anywhere else.

### 6.2 `torch.set_num_threads(os.cpu_count())` was 31× slower — the expensive one

A 20-epoch run was left going for **five hours** and reached roughly **epoch 2**.
Left alone it needed ~40 more hours.

Measured on this 8-core machine, batch 256, seconds per batch:

| threads | 1 | 2 | 3 | 4 | 8 |
|---|---|---|---|---|---|
| s/batch | 1.22 | 0.90 | 0.88 | **0.84** | **26.48** |

There is a **cliff between 4 and 8**. The scan issues ~2000 tiny op launches per
forward (T timesteps × 2 layers × ~8 ops), each on a `[256,32,16]` tensor far too
small to parallelise; at 8 threads the OpenMP barrier and spin-wait cost swamps
the arithmetic. It burns every core while going backwards — which is exactly what
made it deceptive, because 640% CPU looks like healthy progress.

Fix: `--threads` defaulting to **4**, with the table in a comment so nobody
"optimises" it back to `cpu_count()`.

A wrong hypothesis was tested first — denormal floats, which genuinely can cause
10–100× slowdowns in a decaying recurrence — and **disproved** by measurement
(0.76 s vs 0.80 s with denormal-range activations; `set_flush_denormal` made no
difference). What actually located it was measuring **CPU-seconds per batch**,
which is invariant to contention, and dividing the process's accumulated 113,950
CPU-seconds by it.

### 6.3 Redirected logs stayed empty for hours

Python block-buffers stdout at 8 KB when it is not a tty. At ~400 bytes of output
per epoch, a 20-epoch run flushes *at the very end* — the log sat at 0 bytes for
five hours and carried essentially no information about progress.

**`stdbuf -oL` does not fix this**, because CPython does not use libc stdio for
`sys.stdout`. Fix: `sys.stdout.reconfigure(line_buffering=True)` in the script
(`python -u` also works).

This directly caused a bad call: progress was reported as "epoch ~18 of 20" when
it was epoch ~2. A 0-byte log was consistent with *any* epoch from 1 to 19 and
should have been reported as "cannot tell".

### 6.4 Killing the run lost everything

The original `train.py` had its only `torch.save` after the epoch loop, so five
hours of compute vanished on `kill`. Fix: checkpoint on every validation
improvement.

### 6.5 Self-matching process patterns (four times, and counting)

`pkill -f fetch_data.py` matched the shell running it — the command string
contains the pattern — and killed the very command issuing it. The same mistake
then produced a waiter that could never fire:

```bash
until [ ! -e /proc/$(ps -eo pid,args | grep "py/train.py --epochs" | ...) ]
```

whose own command line contains `py/train.py --epochs`, so it resolved to its own
PID and looped forever. (And with an empty PID it degrades to `[ ! -e /proc/ ]`,
also always false.)

**It happened a fourth time on the gate run**, in a session that had already
written this section up:

```bash
until ! kill -0 $(pgrep -f "capture_uart.py --port /dev/ttyUSB1" | head -1); do sleep 5; done
```

— same shape, same cause, spun for 38 minutes after the capture had finished and
had to be killed by hand. Being aware of the trap demonstrably does not prevent
it, because the pattern is written at the moment of *starting* the job, when the
matcher does not exist yet, and it only becomes self-referential once the shell
that runs it is itself in the process table.

**So use the rule, not the warning. Never match a process by its command line
when you can hold its PID:**

```bash
mycmd ... &            # or: exec ... with run_in_background
PID=$!                 # capture at launch, before anything can match it
until ! kill -0 "$PID" 2>/dev/null; do sleep 5; done
```

If a PID genuinely is not available, anchor on something the matcher cannot
contain — a pidfile, or `pgrep -x` on the executable name rather than `-f` on
the full command line.

## 7. Training — `py/train.py` (new, 297 lines)

- **DS2 is read exactly once, at the end.** Epoch selection uses a validation
  split held out from DS1 **by record** (106, 119, 209, 223), not by beat — a
  beat-wise split leaks the patient into model selection, the same reasoning as
  DS1/DS2 one level down.
- **Model selection on macro-F1 over N/S/V only.** F and Q are too rare and too
  unevenly spread to give a stable signal (the holdout has 14 F and no Q), so
  including them makes the selection metric mostly noise. Both still reported on
  test.
- **Inverse-√frequency class weights.** Plain inverse frequency spans 95× between
  N and F, which swamps the gradient with a few hundred beats.
- **N capped at 12,000 in training only** (from 38,096). Consecutive normal beats
  from one patient are near-duplicates, so the rest buys epoch time and little
  else — and epoch time now matters, since the 3-beat window made the scan 2.25×
  more expensive. **Validation and test keep their true distribution**;
  undersampling those would inflate minority-class metrics into meaninglessness.
- **Q dropped from training** (8 beats). Under 1/√count weighting it was receiving
  the *largest* weight in the loss (3.38), letting eight examples compete with
  12,000 N beats at the expense of V and F recall. AAMI EC57 excludes Q from
  reported results anyway. It is still counted in the test report, where it will
  show 0% sensitivity — an honest result rather than a hidden one.
- Reported metrics are per-class **sensitivity and positive predictivity**;
  overall accuracy is printed only because omitting it would look evasive.
  Predicting `N` for everything already scores ~89%.

### Result — run #3 (D=32, N=16), DS2 inter-patient, read once

| class | n | Se% | P+% | F1 |
|---|---|---|---|---|
| N | 44,200 | 89.13 | 94.75 | 0.919 |

## 8. Op budget — the scan is only half the work

Counting integer ops per inference at T=288, D=32, N=16, 2 layers:

| component | ops | share |
|---|---|---|
| **SSM scan** | 1,769,472 | **48.6%** |
| **projections** (dt/B/C/out) | 1,769,472 | **48.6%** |
| LayerNorm elementwise | 73,728 | 2.0% |
| softplus LUT | 18,432 | 0.5% |
| pool + head | 9,376 | 0.3% |

Two conclusions, one reassuring and one not.

**LayerNorm is not a problem — open decision 3 is resolved.** Including a
pessimistic 50-cycle integer rsqrt per timestep, LayerNorm totals **2.8%** of the
work. It is O(T·D) while the scan is O(T·D·N); with N=16 the scan is 16× larger
per timestep. Keep the LayerNorm; do not retrain without it.

**The scan and the projections are exactly 1:1.** If the CV-X-IF instruction
accelerates only the scan, Amdahl's law caps the whole-model speedup at **2.0×**
regardless of how good the accelerator is. `ssm_scan_q15` never exposed this,
because it models the scan alone and has no projections at all — so the "21.9
cycles per inner iteration of headroom" figure in STATUS §6 describes half the
problem.

The ratio is `6DN / (2D² + 2DN)`: projection *parameters* scale as **D²** while
scan *work* scales as **D·N**. So a narrower model with more state shifts work
into the scan at constant parameter count:

| D | N | params | scan:proj | scan share | max speedup |
|---|---|---|---|---|---|
| 32 | 16 (original) | 7,781 | 1.00:1 | 50.0% | 2.00× |
| 24 | 32 | 7,453 | 1.71:1 | 63.2% | 2.71× |
| 16 | 32 | 4,501 | 2.00:1 | 66.7% | 3.00× |
| **16** | **64** | **7,701** | **2.40:1** | **70.6%** | **3.40×** |
| 32 | 32 | 10,917 | — | — | over budget |

**D=16, N=64 is the same parameter budget as the original (7,701 vs 7,781) with
70% more accelerator headroom.** N=64 is also entirely conventional — S4/S4D
commonly use it. It is being trained now alongside the original to check that
accuracy holds; the architectural argument is worthless if the narrow model
cannot learn the task.

This also matters for contribution 3 (the coupling sweep): the sweep measures
timesteps-per-instruction, but the D:N ratio decides how much of the workload is
even *reachable* by the instruction. Worth stating in the writeup as a design
constraint, not an accident.

## 9. Quantization groundwork (items 5-7, paused deliberately)

Two new modules, built while training ran because they are needed whatever the
final architecture turns out to be.

**`py/fixedpoint.py`** -- integer primitives written to *C* semantics, not numpy's:
explicit saturation, int32 accumulators, no float in the inference path, no
silent int64 promotion. That discipline is the whole point: if numpy semantics
leak in, the Python reference and the C port agree on average and diverge in the
tails, which is the hardest kind of hardware bug to find. Validated:

- `rshift_round` -- round-to-nearest arithmetic shift, checked on negatives.
  Truncation biases every value toward zero and that bias compounds through 288
  timesteps of recurrence.
- `softplus_int` -- 256-entry LUT + linear interpolation, **max error 1.83 LSB at
  fa=12**, no `exp()` anywhere. Closed form outside [-8, 8].
- `linear_int` -- max error 1.08e-2 vs float, which is just int8 weight
  granularity at shift 7.
- `check_int32` -- raises on overflow instead of wrapping.

**`py/quantize.py`** -- the integer-only reference the C port must match bit for
bit. `softplus(A_raw)` is folded offline (A is a parameter, so this is free);
only `softplus(dt)` needs the table.

### What it found

**Three genuine int32 overflows**, all of which numpy absorbed silently in int64
and all of which would have been wrong answers on the core with no symptom:

| site | peak | int32 max | fix |
|---|---|---|---|
| `sum(cen^2)` in LayerNorm | 3.4e10 | 2.1e9 | shift down 5 bits before squaring |
| `h.sum(T) << fa` in mean-pool | 3.9e10 | 2.1e9 | divide before scaling |
| `sum(h * Ct)` in the scan | 6.0e9 | 2.1e9 | pre-shift each product by 6 |

The rsqrt was also rewritten as `isqrt` followed by one divide, avoiding a 2**36
intermediate that would have forced 64-bit arithmetic on RV32.

**A measurement trap worth remembering.** The first comparison reported *100%*
float-vs-int agreement. That was meaningless: it sliced the first 128 test beats,
and the test set is ordered by record with record 100 nearly pure N -- so it
compared the two models on a single trivial class. Stratified sampling dropped
the real figure to ~62%. A too-good number deserves the same scrutiny as a bad one.

### The actual blocker: one global scale cannot work

Calibrating the trained model shows activations growing through the network:

```
in_proj out 1.9    block0 out 18.7    block1 out 44.3
state h0    8.9    state h1   36.4
```

Sweeping the activation scale:

| fa | range | agreement | saturations |
|---|---|---|---|
| 12 | +-8 | **62.2%** | 6.6M |
| 9 | +-64 | 60.6% | 5.8M |
| 8 | +-128 | 51.2% | 6.9M |
| 7 | +-256 | 40.9% | 3.6M |

More range genuinely cuts saturation (6.6M -> 3.6M) but costs more precision than
it recovers. That is a real conflict, not a tuning failure: **the input is ~+-1
and needs resolution while the state reaches +-36 and needs range**, and 16 bits
cannot serve both at a single scale. The fix is per-tensor activation scales,
calibrated per site -- standard post-training quantization.

**Paused here on purpose.** Per-tensor calibration is set entirely by activation
ranges, and those change when the model is retrained for the D/N decision (S8).
Building it now would mean building it twice.

**Related, and more important than it looks:** activations growing 1.9 -> 18.7 ->
44.3 across two blocks means this model is *poorly conditioned for quantization*
to begin with. Quantization-aware training, or bounding activations during
training, would make the fixed-point port materially easier. That is a decision
that belongs **before** the final training run, not after it.

## 9b. Quantization, second pass — what the blocker actually was

§9 above concluded the blocker was "one global activation scale". That was
**half right**, and the half that was missing cost more than the half that was
identified. Everything below is measured through the integer path in
`quantize.py`, reproducible with its `--global-fa` and `--per-tensor-weights`
flags.

### The error decomposes into three independent parts, not one

Separating them (fake-quant in float, then confirmed in the integer path):

| configuration | agreement |
|---|---|
| float weights + single global scale (fa=12) | 66.8% |
| float weights + per-tensor activation scales | **99.4%** |
| INT8 per-tensor weights + exact activations | 94.7% |
| INT8 **per-channel** weights + exact activations | **98.9%** |

So per-tensor activation scales were necessary, exactly as §9 said — but INT8
weights cost a further ~5 points that **no amount of activation tuning
recovers** (the activation configuration was swept; the best one was already
optimal). Per-output-channel weight scales buy those back for one indexed shift
per output row in the C port. §9's plan would have topped out around 93%.

### But the dominant error was three hardcoded shift constants

Implementing per-tensor scales *first produced 53%*, worse than the global scale
it replaced. The cause was not the scales. Three constants were sized for worst
cases that never occur, and each was harmless under a global fa and destructive
once fa varied per tensor:

| constant | was | should be | why it mattered |
|---|---|---|---|
| `SV` (LayerNorm variance pre-shift) | 5 | `ceil((1+log2 D)/2)` = **3** | residual stream sits at 9 frac bits, so `cen>>5` left variance 4 frac bits |
| `isqrt(var)` scaling | none | normalise var to top of int32 | var ~2^13 in an int32 register → isqrt returns ~96, ~1% resolution |
| `SP` (scan product pre-shift) | 6 | `log2(N)-1` = **3** at N=16 | three bits discarded on every product in the innermost loop |

Together: **53% → 97%**. That is far more than any activation scale was worth.

The generalisable lesson, and the reason this is written down: *a shift constant
chosen for a worst case that never occurs is invisible while the surrounding
scales are loose, and becomes the dominant error source the moment they get
tight.* All three are now derived from `D`, `N` and the int32 bound rather than
hardcoded, which also means they follow the architecture — at N=64 `SP` must be
5, and the old hardcoded 6 would have been *nearly* right by luck.

Diagnosis method worth reusing: dequantise each site and compare to the float
tensor at the same point (`maxerr` per site). The error appeared at LayerNorm
and compounded downstream; a whole-model agreement number cannot show that.

### Saturation counts are a symptom, not a cause

Before the fixes: 3.3M saturations. After: **0**. The saturations were not a
range problem — they were the *consequence* of upstream precision loss inflating
values. Adding headroom made it worse, which is the tell: `--headroom 1` pushed
`y` saturation from 32% to 41%. If saturation rises when you add range, stop
adding range and go find the error source.

## 9c. The retrain, and a change that had to be reverted

Two changes were made together (per the plan): drop one imbalance correction,
and add a final LayerNorm before the head. **The result was worse on DS2 and the
LayerNorm had to be reverted.**

### Which imbalance correction to drop — settled by measurement

Effective class ratios against DS2's true priors, on this dataset:

| scheme | eff N:V | V over-rep | eff N:S | S over-rep | train beats |
|---|---|---|---|---|---|
| cap 12000 + sqrt weights (run #3) | 2.26 | 6.07x | 4.97 | 4.84x | 15,234 |
| **cap 12000, no weights** | 5.11 | **2.69x** | 24.69 | **0.97x** | 15,234 |
| no cap, sqrt weights | 4.03 | 3.41x | 8.85 | 2.72x | 41,330 |
| neither | 16.22 | 0.85x | 78.39 | 0.31x | 41,330 |

Keeping the cap and dropping the weights is best on *both* classes and 2.7x
cheaper per epoch. It lands S at 0.97x — essentially DS2's exact prior — because
DS1's raw N:S (78:1) is far more skewed than DS2's (24:1) and the 3.17x cap
almost exactly cancels the difference.

### The final LayerNorm: cheap in ops, expensive in bits

Adding `norm_out` before the head looked free — ~0.01% of the op budget, runs
once per inference on `[D]`, never touches the scan. It was not free:

| site | run #3 | with norm_out | growth |
|---|---|---|---|
| residual stream | 50.65 | 221.38 | **4.4x** |
| y (scan output) | 106.62 | 445.03 | 4.2x |
| pooled | 18.74 | 77.51 | 4.1x |
| state h | 48.90 | 55.46 | 1.1x |

**The head reading the pooled vector directly is the only thing penalising an
unbounded residual stream** — weight decay on the head has to pay for a large
pooled scale. Normalising that scale away removes the pressure entirely. The
state barely moved (1.1x), confirming it is the residual path and not the scan.

Consequences: float-vs-int agreement 97.3% → 96.4%, activation scales pushed so
coarse (`res` Q8.7, `y` Q9.6) that **per-channel weight scales stopped helping
at all** (96.41% vs 96.78% per-tensor — activations had become the bottleneck),
and headroom went from harmless to strictly harmful.

Reverted. The comment in `model.py` records why, so it does not get re-added.

> Cheap in operations is not the same as cheap in bits. This project's op-budget
> table (§8) is the right tool for deciding what to accelerate and the *wrong*
> tool for deciding what is safe to add to the model.

### The imbalance hypothesis is not confirmed — and DS2 was read twice

The combined run scored DS2 macro-F1 **0.5071**, against run #3's 0.5596, with V
precision *falling* 59.9% → 37.1% (1,612 N→V false positives became 4,773). That
is the opposite of what STATUS §7.4 predicted.

Three reasons not to conclude anything from it yet:

1. **Two variables changed at once**, so the regression cannot be attributed.
2. **The 0.0525 gap is the same size §7.4 already called single-seed noise.**
3. Validation *improved* (0.6162 → 0.6345) while DS2 fell — §7.4's own lesson,
   repeating.

A third run with the LayerNorm reverted and only the imbalance change is what
actually isolates it.

**`train.py` used to evaluate DS2 at the end of every run**, which quietly
defeats the "read exactly once" policy it was meant to implement: after a few
runs there are several DS2 numbers in the scrollback, and picking the checkpoint
with the best one is selecting on the test set. It is now behind an explicit
`--test` flag, so a DS2 read is a deliberate act visible in shell history.

### New guards

`py/test_fixedpoint.py` (22 checks) and `py/test_quantize.py`. The one that
matters most for the C port: **a batch of N beats gives integers identical to N
runs of 1**, since the core processes one beat at a time — if the reference had
any cross-beat state the two could never agree.

## 9d. The C port, and the gate

**`#GATE,PASS` — 9/9 bit-exact on hardware, 2026-08-09.** Full capture in
`results/gate_20260809_225054.txt`.

### Build the confidence on the host, not on the board

The firmware is baked into the BRAM image, so every change costs a ~15 minute
synthesis run. `fw/ssm_model.c` is therefore plain C99 with no target
dependency, and `py/host_check.c` compiles the *same source* natively and diffs
it against `quantize.py` in about a second. The port was bit-exact on the first
host run and on the first hardware run; that is a consequence of the loop being
fast enough to iterate in, not of getting it right by luck.

Three checks before anything was synthesised, all on 240 beats:

| check | result | what it rules out |
|---|---|---|
| vs `quantize.py` | 240/240 exact | transcription errors |
| `-O0` / `-Os` / `-O2` / `-O3` | identical | reliance on a particular codegen |
| UBSan, `-fno-sanitize-recover` | clean | signed overflow / UB |

The last two are what make a *different compiler on a different ISA* likely to
agree. A port that only passes at one optimisation level is passing by accident.

### Three ways the obvious C is silently wrong

All three are in `ssm_model.c`'s header comment, and all three would have
produced a model that works on most inputs:

1. **numpy `//` floors; C `/` truncates.** They differ only for negative
   operands — and both divisions in the model (the LayerNorm mean, the mean-pool)
   run on sums that go negative. An off-by-one that appears on roughly half of
   all inputs and on *none* of a test set of pure-N beats.
2. **`cen >> SV` is a plain arithmetic shift**, while everything around it is
   round-to-nearest. "Fixing" it for consistency changes the variance.
3. **A shift can be negative.** `FA_RES=9 < FA_POOL=11`, so the mean-pool rescale
   is a *left* shift. A right-shift-only helper silently mangles it.

### The number that matters more than the pass

One inference: **33,874,576 cycles, 27,155,608 instructions, IPC 0.802** — 0.677 s
at 50 MHz. A beat arrives every ~0.8 s at 75 bpm, so **the core sits at ~85% duty
cycle just keeping up**. That is a far better motivation for the accelerator than
any synthetic count, and it belongs in the writeup.

But it is **not yet a valid speedup baseline**. Attributing 48.6% of the time to
the scan (§8) gives 55.8 cycles per inner iteration against `ssm_scan_q15`'s
21.9 — the real kernel is ~2.5× *less* efficient than the hand-written proxy,
because it was written for bit-exactness and has had no optimisation pass:
branchy rounding helpers, a multiply-and-shift per state element, 576 LayerNorms
with hardware divides. Quoting an accelerator speedup against this baseline would
inflate it by roughly that factor, and it is the first thing an examiner will
attack. Optimise `ssm_model.c` first, keeping `host_check` green.

### One loose end: `FA_LOGIT` is the only sample-dependent scale

Sweeping the calibration set from 48 to 1608 beats, **every activation scale is
identical except `logit`**, which lands on 11 or 10 depending on whether a
high-confidence beat happens to be sampled. At 11 the range is ±16 and the
occasional beat clips at the head (measured: 1 value in 0.8% of head outputs).

Left alone deliberately, for two reasons:

- It is **benign**. The logits feed nothing but `argmax`, so clipping the winner
  does not change the winner unless two classes clip together. Saturation in the
  state or residual would be a different matter — that corrupts the recurrence
  and propagates through every later timestep, and it is zero.
- **Changing it now would invalidate a passing gate.** The scales are baked into
  `fw/model_data.h`, so re-exporting means re-synthesising, re-programming and
  re-running the hardware check to keep the `#GATE,PASS` claim honest. Not worth
  spending that on a benign clip.

Bit-exactness is unaffected either way: the C port and `quantize.py` read the
*same* exported scales, so they agree regardless of which value calibration
picked. The sensitivity only matters if the two are calibrated separately —
which is exactly why the scales are exported rather than recomputed.

`test_quantize.py` now asserts the distinction (zero in the recurrent path, <1%
at the head) instead of a blanket zero, which was failing on calibration-set
size rather than on a defect.

### Two traps, one new and one self-inflicted

**`/dev/ttyUSB0` is not necessarily the UART.** The board shows two USB serial
devices — an FT232H (JTAG) and a CH340 (UART) — and which one gets `ttyUSB0`
depends on enumeration order. Capturing on the FT232H returns
`RESULT: SILENT -- no bytes received`, indistinguishable from dead firmware, a
wrong baud, or a bad pin constraint. It cost a full reprogram cycle, because the
firmware prints once at reset and there is no reset button. Resolve by vendor ID
(`1a86`), never by number. Now in STATUS §5.

**§6.5's self-matching process pattern, again.** A waiter built on
`pgrep -f "capture_uart.py --port /dev/ttyUSB1"` matched its own shell, whose
command line contains that string, so it could never exit. This is the *third*
time this pattern has bitten in two days. The fix remains: capture the PID.

   detection, and a QRS detector is the kind of frontend ECG was chosen over

   is done here. **Raise it with him before it is discovered in the viva.**

   `softplus(dt)` needs a 256-entry LUT over [-4, 4].

   capping any scan-only accelerator at 2.0x (§8).** D=16/N=64 raises that to

   Decide before the C port and before the accelerator RTL.
